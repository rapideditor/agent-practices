# agent-practices sync manifest

This file is the single source of truth for what gets synced into downstream projects, at what version, with what instructions. It is consumed by the `/sync` skill that lives in each downstream project.

This file lives at `templates/.sync.manifest.md` in the canonical repo, and is fetched directly by `/sync` (it is **not** itself synced into downstream projects — downstream projects keep their own `.sync.manifest.md` at the repo root, which records what they last received).

Only files under `templates/` are synced. The `playbooks/` and `lessons/` folders at the repo root are never copied downstream; agents fetch them when they're relevant.

## Global rules

These apply to every file unless overridden in the per-file section below:

- **Edit files using the structured file-editing operations exposed by your host environment** — e.g. the `create_file` / `replace_string_in_file` / `multi_replace_string_in_file` tools in VS Code Copilot, the equivalent `Edit` / `Write` tools in Claude Code, Cursor's edit tools, an MCP filesystem server, or whatever your runtime offers. **Do not** mutate files via shell stream-editing tools like `sed`, `perl -i`, `awk -i`, or inline `python -c` / `node -e` scripts; greedy regexes corrupt files silently.
- **Preserve all existing comments** when updating a file. Comments encode domain knowledge.
- **Substitute project-specific values** (project name, repo URL, license holder, author, language/runtime, tool names) using the downstream project's `package.json` (or equivalent manifest) and existing local files as reference. Never invent values — leave a placeholder and flag it if the source of truth is unclear.
- **Never overwrite local-only sections** in a file when the template has no counterpart. Merge, don't replace.
- **Synced files are starting points, and documented drift is expected.** The `Notes` column in the local `.sync.manifest.md` records deliberate differences from the template (see [Local manifest format](#local-manifest-format)). Read a file's local Notes before updating it. Don't undo or re-flag what they describe, but do mention it if the template change touches the same setting. Keep the Notes when you update the row. If you find a local difference that has no note and you keep it, suggest a note in the report.
- **If a file does not exist locally, create it.** If it exists and is at or above the listed version, skip it.
- **Files no longer listed in this manifest are not deleted automatically.** Flag them as orphaned and let the maintainer decide.
- **Strip any legacy trailing sync metadata comment** when updating a file. Earlier versions of this system embedded `<!-- sync: ... -->` (or `# sync:` / `// sync:`) blocks at the end of every synced file. Those are obsolete; metadata now lives only in the manifests. When you touch a file for any reason, remove that trailing block if present.
- **Legacy prompt files.** Reusable prompts used to live at `.github/prompts/<name>.prompt.md` (a Copilot-only format). They are now Agent Skills at `.claude/skills/<name>/SKILL.md`, which both Claude Code and VS Code Copilot discover and show in the `/` menu. When you sync a skill and its legacy prompt file exists locally, carry any project-specific changes from the legacy file into the new skill, then delete the legacy file and remove its row from the local `.sync.manifest.md`. This is a deliberate exception to the no-delete rule: the legacy file has been replaced, not orphaned, and leaving it in place would show the same `/` command twice. Remove `.github/prompts/` if it ends up empty.

## Local manifest format

Each downstream project keeps its own `.sync.manifest.md` at the repo root. `/sync` creates it on the first run and updates a row whenever it writes a file. If an existing local manifest is missing a column, add it.

```markdown
# Local sync manifest

Records scaffold versions received from https://github.com/rapideditor/agent-practices.

| Path | Version | Synced | Canonical Commit | Notes |
|------|---------|--------|------------------|-------|
| `AGENTS.md` | 4 | 2026-11-11 | `afdb584…` | |
| `tsconfig.json` | 3 | 2026-11-12 | `1a2b3c4…` | Adds `declaration` + `isolatedDeclarations` (library that publishes declarations) |
```

- **Version**: the canonical version last written. A missing row means version 0.
- **Synced**: the date of that write.
- **Canonical Commit**: the agent-practices commit SHA it came from, if known.
- **Notes**: deliberate differences from the template, written by the maintainer (or by an agent when asked). `/sync` reads these and keeps them; see the global rules above.

## Per-file instructions

Each instruction below is in the form of a decision: what to do when the file is missing, when it already exists, and what to preserve. If a per-file instruction conflicts with a global rule, the per-file instruction wins.

**Default toward applying the template.** The whole point of this sync system is to propagate minor changes and reworded instructions to many projects at once. The maintainer reviews every diff before committing, so the cost of an over-eager edit is one click to back out — but the cost of an under-eager edit is that an intended update silently fails to propagate. When an instruction says "preserve local content" or similar, that means *preserve project-specific additions and deliberate value changes* (extra steps, custom prose, version pins, paths) — it does **not** mean "avoid touching the file." Refining wording, adopting clearer phrasing, picking up new sections, and updating shared boilerplate are all welcome. The line to hold is: don't strip content that is clearly project-specific, and don't silently change values (versions, paths, config) that the maintainer may have set deliberately — call those out in the report instead.

### `AGENTS.md`
**Bootstrap file** — sync this in Phase 1 of the run, before anything else. Apply the template's structure and wording in full. This means: adopt new sections, **replace existing sections whose template equivalent has changed in structure or content** (e.g. a section that used to be an enumerated list and is now a single paragraph should be replaced wholesale, not preserved), refine wording across all shared sections, and pick up any new "General Guidelines" subsections. The fact that a downstream section currently differs from the template is **not** a signal to preserve it — pattern changes (like removing per-prompt enumerations) are deliberate template-level decisions and should propagate. Renamed sections count as changed: v4 renamed `## Prompt Files` to `## Skills`, so replace the old section rather than keeping both. **Only preserve sections that are genuinely additive** project content with no template counterpart at all (e.g. a "Project Architecture" section, layer/file-path notes). Add those back in their existing positions if they would otherwise be lost.

v6 replaced `## Scratchpad` with `## Project knowledge` (committed notes in `knowledge/`, plus gitignored `PRIVATE.*` files), and renamed `## Shared knowledge` to `## Shared playbooks and lessons`. Replace the old sections, including a project's own working-memory section that points at `SCRATCHPAD.md` or `.scratchpad/`; see the `knowledge/README.md` instructions for moving the notes themselves. If the project already has its own design docs section, keep it and leave out the template's "Design docs" subsection.

### `.claude/skills/sync/SKILL.md`
**Bootstrap file** — sync this in Phase 1 of the run, before anything else. Replace the local file with the source content; this file is intentionally a thin shim and should not accumulate local edits. **If you updated this file in Phase 1, stop the run and tell the user to re-invoke `/sync`** — the currently-running skill is now stale and the new logic only takes effect on the next invocation.

### `.github/prompts/sync.prompt.md`
**Legacy migration shim. Never create this file.** It exists only because older `/sync` prompts (v2 and earlier) bootstrap themselves by fetching this path. Those runs replace their local copy with this shim, and the shim installs `.claude/skills/sync/SKILL.md` in its place. If a current sync run finds this file locally, delete it and remove its row from the local `.sync.manifest.md`, as the "Legacy prompt files" rule describes.

### `README.md`
If the local `README.md` is missing, create it from the template with project-specific values substituted. If it exists, leave the project's actual description, usage, examples, and feature list intact — those are the maintainer's voice. **Everything else is fair game:** adopt new structural sections (badge rows, contributing footer, license block), reword shared boilerplate to match the template, fix outdated phrasing. The maintainer will review and back out anything they want to keep.

### `CONTRIBUTING.md`
Apply the template's structure and wording. For technology-specific sections (language, runtime, package manager, test runner): include only those that apply to this project, adapting install/dev commands from `package.json` or equivalent. Paragraphs marked `optional:` are conditional — include or omit based on whether the condition applies to this project. **Preserve any project-specific sections** that have no template counterpart (e.g. a custom "Running locally" section, project-specific code-of-conduct addendum) — add them back below the template content if they would otherwise be lost.

### `CHANGELOG.md`
If absent, create from the template with project name and repo URL substituted. If present, do not modify the content — record the version bump in `.sync.manifest.md` and move on. The changelog's content is owned by the maintainer's release process, not by sync.

### `LICENSE.md`
Decision order:
1. **If absent**, create from the template using the license type from `package.json`'s `license` field. Substitute the author name and current year.
2. **If present and the license type matches `package.json`**, leave the license text alone but check the copyright year (the `/sync` skill also runs this year check in Phase 3 of every run, even when this file is otherwise up to date). Update only the year (or end-of-range, e.g. `2023–2026` → `2023–2027`) if it is stale relative to the current year. Substitute the author name if different from `package.json`.
3. **If present and the license type contradicts `package.json`'s `license` field**, do not modify the file. Flag the discrepancy in the report and let the maintainer reconcile.

### `RELEASE.md`
If absent, create from the template with project name and repo details substituted. If present, the local file likely has additional project-specific steps (deploy commands, internal notifications, environment-specific checks). Apply the template's wording and structure to the steps that are clearly shared (tagging, changelog updates, version bumping), and preserve project-specific steps in their existing positions. The maintainer reviews the diff — better to refresh the shared content and have one or two extra steps to re-add than to leave outdated wording in place across many projects.

### `tsconfig.json`
Applies only to projects that use TypeScript. Detect by checking `devDependencies.typescript` (or `dependencies.typescript`) in `package.json`.
- **Not applicable** → mark as ⏭️ in the report with reason "project does not use TypeScript". Do not create the file.
- **Applicable** → if absent, create from the template. If present, adopt new compiler options and structural changes from the template. **Do not silently change existing setting values** (target, module, paths, strictness flags) — those may encode deliberate choices. When the template and local file disagree on a value, leave the local value in place and flag the difference in the report so the maintainer can decide.

Specific settings:
- **`types`**: TypeScript 7 no longer loads `@types/*` packages automatically, so the template lists `"bun"`. Without it, the `Bun` global only type-checks if some file happens to import from `'bun'`. Check that `@types/bun` is in `devDependencies`. In a project that doesn't run on Bun, list its runtime's types instead (e.g. `["node"]`).
- **Libraries that publish `.d.ts` files** should consider `"declaration": true` + `"isolatedDeclarations": true`. Exported functions and values then need explicit types, so the public API can't change by accident. Suggest it in the report, but don't add it: in an app it just forces explicit types on every export. If the project already has them, they're deliberate.
- **`tsconfig.build.json`**: libraries often have one that extends `tsconfig.json` and emits declarations only (`emitDeclarationOnly`, `declarationDir`). It isn't a synced file; leave it alone, and expect options the base config leaves out.

### `bunfig.toml`
Applies only to projects that use Bun. Detect by checking `packageManager: bun@*` or `engines.bun` in `package.json`, or the presence of `bun.lockb` / `bun.lock`.
- **Not applicable** → mark as ⏭️ in the report with reason "project does not use Bun". Do not create the file.
- **Applicable** → if absent, create from the template. If present, adopt new keys and structural changes; leave existing values in place when they differ from the template, and flag the differences in the report.

### `.editorconfig`
Replace the local file with the source content, then re-append any local sections that target file types or paths the template does not cover (e.g. a `[*.py]` block at 4 spaces in a Python project). Do not preserve local sections that contradict the template's `[*]` defaults — those are likely stale and the template's defaults are intentional.

### `.gitattributes`
Apply additively. Add any entries from the template that are absent locally. Do not modify or remove entries that exist locally — the maintainer may have configured them deliberately for their project's file types. Flag in the report if the template has entries the local file appears to contradict (different attribute on the same pattern), but do not auto-resolve.

Three exceptions:
- **The `*` line** (`* text=auto eol=lf`) is shared boilerplate, not a project choice. If the local `*` line differs from the template's, replace it, and say so in the report.
- **Attribute values git doesn't recognize** are stale, not deliberate. For example, `text` accepts only `text`, `-text`, `text=auto` and `text=input`, so git silently ignores `* text=lf`. Fix or flag these instead of preserving them.
- **Lines that only set `eol=lf`** for a pattern (e.g. `*.js eol=lf`) repeat what the `*` line already does. Remove them, and say so in the report. Keep lines that set anything else, such as `*.bat eol=crlf` or `-text`.

### `.gitignore`
Merge-only. Add any entries from the template that are absent locally. **Never remove** local-only entries — they almost always reflect project-specific tooling, OS conventions, or editor configurations the template doesn't know about.

### `knowledge/README.md`
The conventions for the project's committed notes. Only this file is synced; the other files in `knowledge/` belong to the project.
- **If absent**, create it from the template. Don't create the other files: they're created when there's something to put in them.
- **If present**, apply the template's shared sections (the files table and conventions), and keep any rows, conventions or sections the project added.

**Moving from `SCRATCHPAD.md`.** If a gitignored `SCRATCHPAD.md` exists at the repo root:
1. Make sure `.gitignore` has `PRIVATE.*` (it's synced before this file).
2. Rename `SCRATCHPAD.md` to `PRIVATE.md`, or append it to `PRIVATE.md` if that already exists. It was written as private, so **never move its contents into committed files on your own.**
3. In the report, list the entries that look safe to publish and where each would go (e.g. design notes → `decisions.md`, known problems → `quirks.md`, open items → `backlog.md`). Move them only once the user agrees, and then remove them from `PRIVATE.md`.

**Moving from `.scratchpad/`.** If the project has a committed `.scratchpad/` folder, `git mv .scratchpad knowledge`, merge its `README.md` with the template as above, and update references to the old path (`git grep -n '\.scratchpad'`).

### `.github/dependabot.yml`
- **If absent**, create from the template. Adapt the `package-ecosystem` entries to match this project's actual dependency managers (npm, cargo, pip, bundler, etc.) — do not include ecosystems the project does not use.
- **If present**, merge additively: add any `package-ecosystem` entries from the template that are absent locally and would apply to this project. Do not modify existing entries' configuration (schedule, directory, reviewers) — those reflect maintainer preference. Flag in the report if the template has structural patterns the local file lacks (grouping rules, version-update strategies).

### `.github/workflows/build.yml`
Applies only to projects that use GitHub Actions and Bun. Detect by checking for an existing `.github/workflows/` directory, and for Bun the same way as `bunfig.toml` above (`packageManager: bun@*` or `engines.bun` in `package.json`, or the presence of `bun.lockb` / `bun.lock`).
- **Not applicable** → mark as ⏭️ in the report with reason. Do not create the file.
- **Applicable** → if absent, create from the template, adapting build steps to match this project's actual `package.json` `scripts`. If present, update action versions to match the template (the maintainer reviews the diff and can revert if a version pin was deliberate), and adopt new structural patterns (caching, matrix builds, timeout settings). **Preserve project-specific steps** that have no template counterpart (deploy steps, custom test runs, environment setup).

Specific settings:
- **`bun install --frozen-lockfile`**: update an existing plain `bun install` step to this. It fails when `bun.lock` doesn't match `package.json`, so CI tests exactly what's committed instead of quietly re-resolving dependencies.
- **`bun-version: latest`** is deliberate: it catches problems with new Bun releases early. That means nothing tests the minimum version in `engines.bun`, which is only advisory (Bun doesn't enforce it). A project that needs to support an older Bun can add a matrix entry for that version; record it in the local manifest's Notes.

Replace the local file with the source content. Project-specific details the hunt relies on (test commands, how to drive the real app, where design docs live) belong in `AGENTS.md`, which the skill reads first, not here.

### `.claude/skills/checkup/SKILL.md`
Replace the local file with the source content. If this project doesn't use Bun, adapt the commands (install, audit, outdated, build and test) to its ecosystem; the skill's "Other ecosystems" table lists the usual equivalents. Project-specific details the checkup relies on (test commands, scripts to avoid running) belong in `AGENTS.md`, which the skill reads first.

### `.claude/skills/commit/SKILL.md`
Replace the local file with the source content. This skill is meant to be uniform across projects; project-specific commit conventions belong in `AGENTS.md` or `CONTRIBUTING.md`, not here.

### `.claude/skills/reflect/SKILL.md`
Replace the local file with the source content. As with the `commit` skill, project-specific overrides belong elsewhere.

### `.claude/skills/release/SKILL.md`
Apply the template's structure and wording, then adapt to this project's release tooling (manual GitHub releases, semantic-release, cargo, changesets, etc.). If the project's release process diverges substantially from the template's assumptions, adopt what's compatible and leave the rest — the maintainer will review the diff and reconcile.

### `.claude/skills/suggest/SKILL.md`
Replace the local file with the source content, then adapt the categories list to this project's stack: keep categories that apply, drop ones that don't (e.g. drop TypeScript-specific categories from a Python project), and add new ones for tooling represented in the local project but not in the template.

### `.claude/skills/triage/SKILL.md`
Replace the local file with the source content. Project-specific triage conventions (label meanings, what's out of scope, issue templates) belong in `AGENTS.md` or `CONTRIBUTING.md`, which the skill reads first.

## Versioning policy

- Increment a file's version on any meaningful semantic change.
- Cosmetic changes (typos, whitespace) do not require a version bump.
- A version bump in this manifest will cause every downstream project to update on next `/sync`.
- When adding a new file to the manifest, add it to **both** the version table and the per-file instructions section. Every entry must appear in both.
