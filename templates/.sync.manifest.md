# agent-practices sync manifest

This file is the single source of truth for what gets synced into downstream projects, at what version, with what instructions. It is consumed by the `/sync` prompt that lives in each downstream project.

This file lives at `templates/.sync.manifest.md` in the canonical repo, and is fetched directly by `/sync` (it is **not** itself synced into downstream projects — downstream projects keep their own `.sync.manifest.md` at the repo root, which records what they last received).

## Global rules

These apply to every file unless overridden in the per-file section below:

- **Edit files using the structured file-editing operations exposed by your host environment** — e.g. the `create_file` / `replace_string_in_file` / `multi_replace_string_in_file` tools in VS Code Copilot, the equivalent `Edit` / `Write` tools in Claude Code, Cursor's edit tools, an MCP filesystem server, or whatever your runtime offers. **Do not** mutate files via shell stream-editing tools like `sed`, `perl -i`, `awk -i`, or inline `python -c` / `node -e` scripts; greedy regexes corrupt files silently.
- **Preserve all existing comments** when updating a file. Comments encode domain knowledge.
- **Substitute project-specific values** (project name, repo URL, license holder, author, language/runtime, tool names) using the downstream project's `package.json` (or equivalent manifest) and existing local files as reference. Never invent values — leave a placeholder and flag it if the source of truth is unclear.
- **Never overwrite local-only sections** in a file when the template has no counterpart. Merge, don't replace.
- **If a file does not exist locally, create it.** If it exists and is at or above the listed version, skip it.
- **Files no longer listed in this manifest are not deleted automatically.** Flag them as orphaned and let the maintainer decide.
- **Strip any legacy trailing sync metadata comment** when updating a file. Earlier versions of this system embedded `<!-- sync: ... -->` (or `# sync:` / `// sync:`) blocks at the end of every synced file. Those are obsolete; metadata now lives only in the manifests. When you touch a file for any reason, remove that trailing block if present.

## Per-file instructions

Each instruction below is in the form of a decision: what to do when the file is missing, when it already exists, and what to preserve. If a per-file instruction conflicts with a global rule, the per-file instruction wins.

**Default toward applying the template.** The whole point of this sync system is to propagate minor changes and reworded instructions to many projects at once. The maintainer reviews every diff before committing, so the cost of an over-eager edit is one click to back out — but the cost of an under-eager edit is that an intended update silently fails to propagate. When an instruction says "preserve local content" or similar, that means *preserve project-specific additions and deliberate value changes* (extra steps, custom prose, version pins, paths) — it does **not** mean "avoid touching the file." Refining wording, adopting clearer phrasing, picking up new sections, and updating shared boilerplate are all welcome. The line to hold is: don't strip content that is clearly project-specific, and don't silently change values (versions, paths, config) that the maintainer may have set deliberately — call those out in the report instead.

### `AGENTS.md`
**Bootstrap file** — sync this in Phase 1 of the run, before anything else. Apply the template's structure and wording in full. This means: adopt new sections, **replace existing sections whose template equivalent has changed in structure or content** (e.g. a section that used to be an enumerated list and is now a single paragraph should be replaced wholesale, not preserved), refine wording across all shared sections, and pick up any new "General Guidelines" subsections. The fact that a downstream section currently differs from the template is **not** a signal to preserve it — pattern changes (like removing per-prompt enumerations) are deliberate template-level decisions and should propagate. **Only preserve sections that are genuinely additive** project content with no template counterpart at all (e.g. a "Project Architecture" section, working-memory conventions specific to this codebase, layer/file-path notes). Add those back in their existing positions if they would otherwise be lost.

### `.github/prompts/sync.prompt.md`
**Bootstrap file** — sync this in Phase 1 of the run, before anything else. Replace the local file with the source content; this file is intentionally a thin shim and should not accumulate local edits. **If you updated this file in Phase 1, stop the run and tell the user to re-invoke `/sync`** — the currently-running prompt is now stale and the new logic only takes effect on the next invocation.

### `README.md`
If the local `README.md` is missing, create it from the template with project-specific values substituted. If it exists, leave the project's actual description, usage, examples, and feature list intact — those are the maintainer's voice. **Everything else is fair game:** adopt new structural sections (badge rows, contributing footer, license block), reword shared boilerplate to match the template, fix outdated phrasing. The maintainer will review and back out anything they want to keep.

### `CONTRIBUTING.md`
Apply the template's structure and wording. For technology-specific sections (language, runtime, package manager, test runner): include only those that apply to this project, adapting install/dev commands from `package.json` or equivalent. Paragraphs marked `optional:` are conditional — include or omit based on whether the condition applies to this project. **Preserve any project-specific sections** that have no template counterpart (e.g. a custom "Running locally" section, project-specific code-of-conduct addendum) — add them back below the template content if they would otherwise be lost.

### `CHANGELOG.md`
If absent, create from the template with project name and repo URL substituted. If present, do not modify the content — record the version bump in `.sync.manifest.md` and move on. The changelog's content is owned by the maintainer's release process, not by sync.

### `LICENSE.md`
Decision order:
1. **If absent**, create from the template using the license type from `package.json`'s `license` field. Substitute the author name and current year.
2. **If present and the license type matches `package.json`**, leave the license text alone but check the copyright year. Update only the year (or end-of-range, e.g. `2023–2026` → `2023–2027`) if it is stale relative to the current year. Substitute the author name if different from `package.json`.
3. **If present and the license type contradicts `package.json`'s `license` field**, do not modify the file. Flag the discrepancy in the report and let the maintainer reconcile.

### `RELEASE.md`
If absent, create from the template with project name and repo details substituted. If present, the local file likely has additional project-specific steps (deploy commands, internal notifications, environment-specific checks). Apply the template's wording and structure to the steps that are clearly shared (tagging, changelog updates, version bumping), and preserve project-specific steps in their existing positions. The maintainer reviews the diff — better to refresh the shared content and have one or two extra steps to re-add than to leave outdated wording in place across many projects.

### `tsconfig.json`
Applies only to projects that use TypeScript. Detect by checking `devDependencies.typescript` (or `dependencies.typescript`) in `package.json`.
- **Not applicable** → mark as ⏭️ in the report with reason "project does not use TypeScript". Do not create the file.
- **Applicable** → if absent, create from the template. If present, adopt new compiler options and structural changes from the template. **Do not silently change existing setting values** (target, module, paths, strictness flags) — those may encode deliberate choices. When the template and local file disagree on a value, leave the local value in place and flag the difference in the report so the maintainer can decide.

### `bunfig.toml`
Applies only to projects that use Bun. Detect by checking `packageManager: bun@*` in `package.json`, or the presence of `bun.lockb` / `bun.lock`.
- **Not applicable** → mark as ⏭️ in the report with reason "project does not use Bun". Do not create the file.
- **Applicable** → if absent, create from the template. If present, adopt new keys and structural changes; leave existing values in place when they differ from the template, and flag the differences in the report.

### `.editorconfig`
Replace the local file with the source content, then re-append any local sections that target file types or paths the template does not cover (e.g. a `[*.py]` block at 4 spaces in a Python project). Do not preserve local sections that contradict the template's `[*]` defaults — those are likely stale and the template's defaults are intentional.

### `.gitattributes`
Apply additively. Add any entries from the template that are absent locally. Do not modify or remove entries that exist locally — the maintainer may have configured them deliberately for their project's file types. Flag in the report if the template has entries the local file appears to contradict (different attribute on the same pattern), but do not auto-resolve.

### `.gitignore`
Merge-only. Add any entries from the template that are absent locally. **Never remove** local-only entries — they almost always reflect project-specific tooling, OS conventions, or editor configurations the template doesn't know about.

### `.github/dependabot.yml`
- **If absent**, create from the template. Adapt the `package-ecosystem` entries to match this project's actual dependency managers (npm, cargo, pip, bundler, etc.) — do not include ecosystems the project does not use.
- **If present**, merge additively: add any `package-ecosystem` entries from the template that are absent locally and would apply to this project. Do not modify existing entries' configuration (schedule, directory, reviewers) — those reflect maintainer preference. Flag in the report if the template has structural patterns the local file lacks (grouping rules, version-update strategies).

### `.github/workflows/build.yml`
Applies only to projects that use GitHub Actions and Bun. Detect by checking for an existing `.github/workflows/` directory and `packageManager: bun@*` in `package.json`.
- **Not applicable** → mark as ⏭️ in the report with reason. Do not create the file.
- **Applicable** → if absent, create from the template, adapting build steps to match this project's actual `package.json` `scripts`. If present, update action versions to match the template (the maintainer reviews the diff and can revert if a version pin was deliberate), and adopt new structural patterns (caching, matrix builds, timeout settings). **Preserve project-specific steps** that have no template counterpart (deploy steps, custom test runs, environment setup).

### `.github/prompts/commit.prompt.md`
Replace the local file with the source content. This prompt is meant to be uniform across projects; project-specific commit conventions belong in `AGENTS.md` or `CONTRIBUTING.md`, not here.

### `.github/prompts/reflect.prompt.md`
Replace the local file with the source content. As with `commit.prompt.md`, project-specific overrides belong elsewhere.

### `.github/prompts/release.prompt.md`
Apply the template's structure and wording, then adapt to this project's release tooling (manual GitHub releases, semantic-release, cargo, changesets, etc.). If the project's release process diverges substantially from the template's assumptions, adopt what's compatible and leave the rest — the maintainer will review the diff and reconcile.

### `.github/prompts/suggest.prompt.md`
Replace the local file with the source content, then adapt the categories list to this project's stack: keep categories that apply, drop ones that don't (e.g. drop TypeScript-specific categories from a Python project), and add new ones for tooling represented in the local project but not in the template.

## Versioning policy

- Increment a file's version on any meaningful semantic change.
- Cosmetic changes (typos, whitespace) do not require a version bump.
- A version bump in this manifest will cause every downstream project to update on next `/sync`.
- When adding a new file to the manifest, add it to **both** the version table and the per-file instructions section. Every entry must appear in both.
